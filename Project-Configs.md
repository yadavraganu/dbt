## 1. The big picture

A **dbt project** is simply a folder that contains a file named `dbt_project.yml`. That file is what tells dbt "this directory is a project" and also tells dbt *how to behave* inside it.

```
my_dbt_project/
├── dbt_project.yml      ← required; the project config file
├── models/              ← SQL models, sources, unit tests
├── seeds/               ← CSV files
├── snapshots/           ← snapshot definitions
├── macros/              ← Jinja macros
├── analyses/            ← ad-hoc SQL that is compiled, not run
├── tests/               ← singular tests (+ tests/generic for custom generic tests)
├── target/              ← compiled output & artifacts (generated)
├── dbt_packages/        ← installed packages (generated by `dbt deps`)
└── .dbtignore           ← optional; files dbt should pretend don't exist
```

The "Project configs" section of the reference documents **every key** you can put in `dbt_project.yml`, plus two related files (`.dbtignore` and `dbt_cloud.yml`).

**Mental model:** project configs answer questions like

| Question | Config |
|---|---|
| What is this project called? | `name` |
| Which warehouse connection does it use? | `profile` |
| Where do my models / seeds / macros live? | `model-paths`, `seed-paths`, `macro-paths`, … |
| Which dbt versions is it allowed to run on? | `require-dbt-version` |
| Should dbt quote identifiers? | `quoting` |
| What should run before/after every dbt command? | `on-run-start`, `on-run-end` |

## 2. `dbt_project.yml` — the heart of every project

- **Required** for every dbt project.
- dbt looks for it in the **current working directory and its parents**. You can point to another location with the `--project-dir` flag (or, in dbt v1.11+, the `DBT_ENGINE_PROJECT_DIR` environment variable).
- On the dbt platform, the project ID goes in the `dbt-cloud` block of this file (see [section 9](#9-companion-files)).
- You **cannot** define a *property* in `dbt_project.yml` unless it is also a *config*. Example: macro properties can't be set here.
- It uses **YAML** — so be comfortable with strings, lists (arrays), and dictionaries (maps).

## 3. Syntax rules you must know

### 3.1 The `+` prefix

In `dbt_project.yml`, dbt needs to tell the difference between **a folder name** and **a config name**. It does this with a `+` in front of config names.

```yaml
models:
  +materialized: view          # a config → applies to everything
  jaffle_shop:                 # a folder / project name (no plus)
    marts:                     # a sub-folder (no plus)
      +materialized: table     # a config for models/marts/**
```

Key points:

- The `+` is used for **configs only**, and only in `dbt_project.yml` under a resource key (`models`, `seeds`, …).
- It does **not** apply to the `config()` Jinja macro in a `.sql` file, or to the `config:` property inside a `.yml` file.
- It is not compatible with `config-version: 1` (which is deprecated anyway).
- It's *required* when a config takes a dictionary value (e.g. `+persist_docs`) or when a config name collides with a folder name (e.g. you have a `models/tags/` folder and also use the `tags` config).
- Don't confuse this with the *other* `+` used in `.yml`/`.sql` files to control merge behaviour (clobber vs. add) — that's a different feature.

### 3.2 Naming conventions (dashes vs underscores)

| Where | Rule | Example |
|---|---|---|
| `saved-queries` and `semantic-models` **in `dbt_project.yml`** | use **dashes** | `saved-queries:` |
| `data_tests` and `unit_tests` **everywhere, including `dbt_project.yml`** | use **underscores** | `data_tests:` |
| Multi-word resource types in **other YAML files** | use **underscores** | `saved_queries:` |
| Project-level keys like `model-paths`, `on-run-start` | **dashes** | `model-paths:` |

```yaml
# dbt_project.yml
saved-queries:           # dashes here
  my_saved_query:
    +cache:
      enabled: true

data_tests:              # underscores here
  +store_failures: true

unit_tests:
  +enabled: true
```

```yaml
# models/saved_queries.yml  (a properties file)
saved_queries:           # underscores outside dbt_project.yml
  - name: saved_query_name
    config:
      cache:
        enabled: true
```

## 4. Identity configs

### 4.1 `name` (required)

```yaml
name: jaffle_shop
```

- The name of your project. **Letters, digits and underscores only. Cannot start with a digit.**
- Recommendation: use your organisation (or main project) name in `snake_case` — `acme`, `jaffle_shop`, `evilcorp`.
- ❌ Hyphens are invalid. You'll see an error like:

  ```
  at path ['name']: 'jaffle-shop' does not match '^[^\d\W]\w*$'
  ```
  Fix: `name: jaffle_shop`.

The project name is also the first key you use under `models:` / `seeds:` etc. to target your own project's resources.

### 4.2 `version` (optional since dbt 1.5)

The word "version" shows up in several places in dbt and means different things:

| Location | Meaning |
|---|---|
| `version:` in **`dbt_project.yml`** | The version of *your project* (use semantic versioning like `1.0.0`). Optional from dbt v1.5; default `None`. Required (but unused) on v1.4 and lower. |
| `version:` at the top of a **`.yml` property file** | Control tag telling dbt how to parse that YAML. Only `2` is accepted. Optional from v1.5. |
| `versions:` / `v:` on a **model** | *Model versions* — a governance feature for evolving model contracts. Totally separate from the above. |

```yaml
# dbt_project.yml
version: "1.0.0"
```

```yaml
# models/schema.yml  (optional header)
version: 2
models:
  - name: customers
```

### 4.3 `config-version` (optional)

```yaml
config-version: 2
```

- Declares that your `dbt_project.yml` uses the **v2 structure**.
- If you omit it, dbt assumes v2. **Version 1 is deprecated.**
- Safe to leave in for clarity; safe to leave out.

### 4.4 `profile`

```yaml
profile: jaffle_shop
```

- Names the **profile** (in `profiles.yml`) that holds your warehouse connection.
- **Developing locally:** required — *unless* you pass `--profile` on the command line, which overrides this.
- **Developing in the dbt platform:** not applicable (connection is managed in the UI).
- Recommendation: use your org name in `snake_case`; optionally include the warehouse if you have several: `acme_snowflake`, `jaffle_shop_bigquery`, `jaffle_shop_redshift`.

## 5. Directory path configs

All of these answer the question **"where does dbt look for X?"** They share the same rules:

- Value is a **list of directories** (`[...]`), except where noted.
- Paths must be **relative to `dbt_project.yml`**. Never use absolute paths such as `/Users/me/project/models` — it causes unexpected behaviour.
- Setting the config **replaces** the default; it doesn't add to it (include the default too if you still want it).

```yaml
# ✅ Do
model-paths: ["models"]

# ❌ Don't
model-paths: ["/Users/username/project/models"]
```

| Config | What lives there | Default | Notes |
|---|---|---|---|
| `model-paths` | Models, **sources**, and **unit tests** | `["models"]` | Core folder of every project. |
| `seed-paths` | Seed CSV files | `["seeds"]` | Can share a folder with models (see below). |
| `test-paths` | **Singular** tests and **custom generic** tests | `["tests"]` | Generic test definitions go in `tests/generic`; every other `.sql` file is a singular test. |
| `analysis-paths` | Analyses (compiled `.sql`, never materialised) | not set by default, but `dbt init` writes `["analyses"]` | Without this config, dbt compiles no `.sql` files as analyses. |
| `macro-paths` | Macros | `["macros"]` | You **cannot** co-locate models and macros. |
| `snapshot-paths` | Snapshots | `["snapshots"]` | From dbt v1.9, snapshots written in the newer YAML syntax can live alongside models. |
| `docs-paths` | `{% docs %}` blocks | *all resource paths* (v1.9+) | If you set it, dbt looks **only** there. Docs say they typically omit it and keep the default. |
| `asset-paths` | Images/files copied into `target/` on `dbt docs generate` | `[]` (nothing copied) | Lets you render repo images inside your project docs. |
| `function-paths` | User-defined functions (UDFs) | `["functions"]` | Newer feature. |
| `osi-paths` | Ossie semantic-layer documents | `["OSI"]` | Available from dbt v1.12 (or the "v1 Latest" release track). |
| `check-paths` | Checks | `["checks"]` | **Available in dbt v2.** |
| `skill-paths` | Agent skills (each sub-folder with a `SKILL.md` is one skill) | `["skills"]` | dbt scans your root project *and* installed packages. |

### Examples

```yaml
# Rename the models folder
model-paths: ["transformations"]

# Use two seed folders  (docs recommend sub-folders inside seeds/ instead)
seed-paths: ["seeds", "custom_seeds"]

# Co-locate seeds and models — works because seeds are .csv and models are .sql
seed-paths: ["models"]
model-paths: ["models"]

# Singular tests in a custom folder
test-paths: ["custom_tests"]

# Analyses
analysis-paths: ["analyses"]

# Macros in a custom folder
macro-paths: ["custom_macros"]

# Old-style name for snapshots
snapshot-paths: ["archives"]

# Docs blocks in one folder only
docs-paths: ["docs"]

# Copy images into target/ for docs
asset-paths: ["assets"]

# Several UDF folders
function-paths: ["functions", "custom_udfs"]

# Several skill folders
skill-paths: ["skills", "team-skills"]

# Multiple check folders (dbt v2)
check-paths: ["checks", "shared_checks"]
```

### Gotchas

- `analysis-paths`: because there's no built-in default, a missing config means analyses are silently ignored. `dbt init` sets it for you.
- `docs-paths`: leaving it unset is usually best — dbt scans all resource folders for docs blocks.
- Co-location only works when the **file types differ** (seeds = `.csv`, models = `.sql`). Models + macros is explicitly not allowed.

## 6. Build/cleanup configs

### 6.1 `packages-install-path`

```yaml
packages-install-path: dbt_packages     # default
```

- Folder where `dbt deps` installs packages.
- Default is `dbt_packages`. Normally **git-ignored**.
- Note: it's a **single directory string**, not a list.

### 6.2 `clean-targets`

```yaml
clean-targets: [target, dbt_packages]   # what `dbt init` gives you
```

- Directories deleted when you run **`dbt clean`**.
- Only list folders that contain **generated artifacts** (compiled files, logs, installed packages) — never source code!
- **Default if omitted:** `dbt clean` removes the contents of your `target-path`.
- Preferred setup: include both `target` and `dbt_packages` so `dbt clean` also wipes installed packages. Add `logs` too if you want logs gone:

```yaml
clean-targets: [target, dbt_packages, logs]
```

> ⚠️ If you change `packages-install-path`, remember to update `clean-targets` to match.

## 7. Behaviour configs

### 7.1 `quoting`

Controls whether dbt wraps **database**, **schema** and **identifier** names in quotes when it:
1. creates relations (tables/views), and
2. resolves a `ref()` into a direct relation reference.

```yaml
quoting:
  database: true | false
  schema: true | false
  identifier: true | false
  snowflake_ignore_case: true | false   # dbt v2 only
```

- **BigQuery:** use `database` and `schema` keys here; they apply to **project** and **dataset** names respectively.
- **Defaults vary by adapter.**
  - Most adapters: all `true`. Why? Quoting lets you use reserved words/special characters (though avoiding them is still advised).
  - Snowflake: all `false`.

**Example — disable quoting:**

```yaml
quoting:
  database: false
  schema: false
  identifier: false
```
Result: `create table analytics.dbt_alice.dim_customers` (no quotes).

#### Warehouse-specific advice

**Snowflake** — recommended: set all quoting to `false`.
- Snowflake *uppercases* unquoted names but *preserves case* of quoted names. dbt's convention is lowercase model names, so a quoted `"analytics"."orders"` would only be queryable with quotes + exact lowercase — which breaks BI tools and ad-hoc SQL.
- Downside of `false`: you can't use reserved words as model/table names (you shouldn't anyway).
- **dbt v2 + `QUOTED_IDENTIFIERS_IGNORE_CASE = true`** (e.g. set by an orchestrator or pre-hook): enable quoting **and** `snowflake_ignore_case: true` to keep compile-time identifier handling consistent with runtime and avoid "column not found" errors.
- Quoted source table? Configure quoting on the *source* (see "resource-properties → quoting").

**Redshift** — keep the defaults (omit the config, or all `true`).
- Redshift lowercases names, even quoted ones, unless the cluster/workgroup setting `enable_case_sensitive_identifier` is `true`.
- `quoting` only controls whether dbt sends double quotes — it can't work around lowercasing. If you need mixed-case names: turn on `enable_case_sensitive_identifier` **and** keep quoting on.

**Other warehouses** — leave defaults.

### 7.2 `query-comment`

dbt can **inject a comment into every SQL query** it runs — super useful for attributing warehouse cost/queries to dbt resources.

Simple form:
```yaml
query-comment: "executed by dbt"
```

Dictionary form:
```yaml
query-comment:
  comment: string
  append: true | false      # default false → comment goes at the TOP
  job-label: true | false   # BigQuery only
```

**Default behaviour:** dbt adds a JSON comment containing the app, dbt version, profile, target and node ID. For Snowflake it's placed at the **end** of the query (Snowflake strips leading comments); for other adapters it's placed at the **start**.

```sql
/* {"app": "dbt", "dbt_version": "...", "profile_name": "debug",
    "target_name": "dev", "node_id": "model.dbt2.my_model"} */
create view analytics.analytics.orders as ( select ... );
```

**Recipes**

| Goal | Config |
|---|---|
| Static comment | `query-comment: "executed by dbt"` |
| Disable comments | `query-comment:` (empty) **or** `query-comment: null` |
| Dynamic comment | `query-comment: "run by {{ target.user }} in dbt"` |
| Append the default comment | `query-comment:` + `append: True` (omit `comment`) |
| Append a custom comment | `comment: "run by {{ target.user }} in dbt"` + `append: True` |
| BigQuery job labels | `query-comment:` + `job-label: True` |
| Generate with a macro | `query-comment: "{{ query_comment() }}"` |

**Macro example (basic)** — `macros/query_comment.sql`:
```jinja
{% macro query_comment() %}
  dbt {{ dbt_version }}: running {{ node.unique_id }} for target {{ target.name }}
{% endmacro %}
```
```yaml
query-comment: "{{ query_comment() }}"   # quote it so YAML doesn't read { as a dict
```

**Macro example (advanced)** — builds a JSON comment with file path, node id, resource type, package, and relation (database/schema/identifier) that you can parse later to analyse performance:
```jinja
{% macro query_comment(node) %}
    {%- set comment_dict = {} -%}
    {%- do comment_dict.update(
        app='dbt',
        dbt_version=dbt_version,
        profile_name=target.get('profile_name'),
        target_name=target.get('target_name'),
    ) -%}
    {%- if node is not none -%}
      {%- do comment_dict.update(
        file=node.original_file_path,
        node_id=node.unique_id,
        node_name=node.name,
        resource_type=node.resource_type,
        package_name=node.package_name,
        relation={
            "database": node.database,
            "schema": node.schema,
            "identifier": node.identifier
        }
      ) -%}
    {% else %}
      {%- do comment_dict.update(node_id='internal') -%}
    {%- endif -%}
    {% do return(tojson(comment_dict)) %}
{% endmacro %}
```
```yaml
query-comment: "{{ query_comment(node) }}"
```

**Context variables available inside a query-comment:**

| Variable | Description |
|---|---|
| `dbt_version` | The dbt version in use |
| `env_var` | Read environment variables |
| `modules` | Python modules exposed to Jinja |
| `run_started_at` | When the invocation began |
| `invocation_id` | Unique ID of the invocation |
| `fromjson` / `tojson` | JSON helpers |
| `log` | Logging |
| `var` | Project variables (⚠️ see note) |
| `target` | Active target info |
| `connection_name` | dbt-generated internal connection name |
| `node` | Dict of the parsed node (`node.unique_id`, `node.schema`, …) |

> ⚠️ `var()` inside query-comment macros only sees variables passed via **`--vars` on the CLI** — *not* the `vars:` block of `dbt_project.yml`.

### 7.3 `dispatch`

```yaml
dispatch:
  - macro_namespace: packagename
    search_order: [packagename, other_package]
```

- Overrides where dbt looks for implementations when a macro is called via `adapter.dispatch()`.
- **Default:** search your **root project first**, then the package named by `macro_namespace`.
- Use cases:

```yaml
# 1) "Shim" dbt_utils with the spark_utils compatibility package
dispatch:
  - macro_namespace: dbt_utils
    search_order: ['spark_utils', 'dbt_utils']

# 2) Your root project's re-implementations win, fall back to dbt_utils (this is also the default)
dispatch:
  - macro_namespace: dbt_utils
    search_order: ['my_root_project', 'dbt_utils']
```

### 7.4 `on-run-start` & `on-run-end` (project-level hooks)

```yaml
on-run-start: sql-statement | [sql-statement]
on-run-end:   sql-statement | [sql-statement]
```

Run SQL (or a macro returning SQL) at the **start/end** of these commands:
`dbt build`, `dbt compile`, `dbt docs generate`, `dbt run`, `dbt seed`, `dbt snapshot`, `dbt test`.

- `on-run-end` has **extra Jinja variables** (e.g. `schemas`, `results`) — see the "on-run-end context" page.

```yaml
# Grant usage on every schema dbt touched, at the end of the run
on-run-end:
  - "{% for schema in schemas %}grant usage on schema {{ schema }} to group reporter; {% endfor %}"

# Or call a macro
on-run-end: "{{ grant_select(schemas) }}"
```

More examples live in the "Hooks and operations" page of the docs.

## 8. Version guard: `require-dbt-version`

```yaml
require-dbt-version: ">=1.10.0,<3.0.0"
# or as a list
require-dbt-version: [">=1.10.0", "<3.0.0"]
```

**What it does**
- Restricts the project to a **range of dbt versions**.
- If an installed **package** declares a `require-dbt-version` your dbt doesn't satisfy, dbt errors out.
- Helps package maintainers (e.g. dbt-utils) guarantee compatibility.
- Signals **dbt v2 compatibility** (a range that includes `2.0.0` or higher).
- Keeps a whole team on compatible versions locally.
- If you don't set it → **no check happens**.
- On the **dbt platform with a release track**, this config is **ignored**.

**YAML quoting rules** (it must reach the parser as a string):

```yaml
# ✅ works
require-dbt-version: ">=1.0.0"
require-dbt-version: '>=1.0.0'

# ❌ doesn't work
require-dbt-version: >=1.0.0        # no quotes
require-dbt-version: ">= 1.0.0"     # whitespace after the operator
```

**Best practice — always give BOTH bounds.** An unbounded `">=1.0.0"` may break the day a new major version ships. Pin to a range such as `">=1.10.0,<3.0.0"`.

**Variants**

| Goal | Value |
|---|---|
| Minimum only (not recommended alone) | `">=1.9.0"` |
| dbt v2 only | `">=2.0.0"` |
| Range (recommended) | `">=1.10.0,<3.0.0"` |
| Exact version (discouraged) | `"1.5.0"` |

**dbt v2 note:** if your range *excludes* `2.0.0` (e.g. `>=1.6.0,<2.0.0`), dbt v2 shows a **warning now and will become an error** in a future release.

**Failure message example**
```
Running with dbt=1.5.0
Encountered an error while reading the project:
  This version of dbt is not supported with the 'my_project' package.
    Installed version of dbt: =1.5.0
    Required version of dbt for 'my_project': ['>=1.6.0', '<2.0.0']
  Check the requirements for the 'my_project' package, or run dbt again with --no-version-check
```

**Bypass:** `dbt run --no-version-check`.

**Related tips from the docs**
- `dbt-autofix` scans your project for deprecated configs and helps with v2 migration; it also upgrades packages to the lowest version supporting dbt v2.
- *Using packages:* pin to a specific revision/version bound; `dbt deps` locks versions for predictable builds.
- *Writing packages:* code defensively, e.g. check a global macro exists before using it:
  ```jinja
  {% if not dbt.get('date_spine') %}
    {{ exceptions.raise_compiler_error("Expected to find the dbt.date_spine macro, but it could not be found") }}
  {% endif %}
  ```

## 9. Companion files

### 9.1 `.dbtignore`

Put it in the **project root**. It works exactly like `.gitignore` (same syntax). Anything matching is **not read, parsed, or detected** by dbt — as though it didn't exist.

```gitignore
# ignore individual files
not-a-dbt-model.py
another-non-dbt-model.py

# ignore all .py files
**.py

# ignore .py files containing "codegen" in the name
*codegen*.py

# ignore everything in a folder tree
path/to/folders/**

# ignore a specific sub-folder
path/to/folders/subfolder/**
```

Handy for helper scripts, vendored code, or draft files living inside model folders.

### 9.2 `dbt_cloud.yml` (dbt platform only)

A **credentials file** used by the **dbt platform CLI** and the **dbt VS Code extension** to authenticate with the dbt platform. It lives in your **`~/.dbt/`** directory.

> 🔐 It contains **API keys / a personal access token**. Never commit it to version control.

**How to get it**
1. In the dbt platform, pick a project that has a **development environment**.
2. Go to **Account settings → Your profile**.
3. - CLI: **CLI → Configure Cloud authentication → Download CLI configuration file**
   - VS Code extension: **VS Code Extension → Set up your credentials → Download credentials**
4. Move it into `.dbt/`:
   ```bash
   mkdir -p ~/.dbt && mv ~/Downloads/dbt_cloud.yml ~/.dbt/dbt_cloud.yml     # Mac/Linux
   ```
   ```bat
   move %USERPROFILE%\Downloads\dbt_cloud.yml %USERPROFILE%\.dbt\dbt_cloud.yml   :: Windows
   ```
- If the download is named like `dbt_cloud(2).yml`, **rename it** to exactly `dbt_cloud.yml`; the tools only look for that exact name.
- Make sure the `project-id` in your `dbt_project.yml` `dbt-cloud` block matches the project you're working on.

**Structure**

```yaml
version: "1"
context:
  active-host: your_active_host          # e.g. "abc123.us1.dbt.com"
  active-project: your_project_id        # e.g. "123456"
projects:
  - project-name: your_project_name
    project-id: your_project_id
    account-name: your_account_name
    account-id: your_account_id
    account-host: your_account_host
    token-name: your_token_name          # e.g. "cloud-cli-1234"
    token-value: your_token_value        # SECRET
```

**Field reference**

| Field | Required | Meaning |
|---|---|---|
| `version` | Yes | Schema version of the file (currently `"1"`) |
| `context.active-host` | Yes | Default `account-host` |
| `context.active-project` | Yes | Default `project-id` (must exist under `projects`) |
| `context.defer-env-id` | No | Environment to defer to for build artifacts (CLI only) |
| `projects.project-name` | Yes | Human-readable project name |
| `projects.project-id` | Yes | dbt platform project ID (visible in the project URL) |
| `projects.account-name` | Yes | Human-readable account name |
| `projects.account-id` | Yes | dbt platform account ID |
| `projects.account-host` | Yes | e.g. `cloud.getdbt.com`, `emea.dbt.com`, or your single-tenant URL |
| `projects.token-name` | Yes | Name of the personal access token |
| `projects.token-value` | Yes | The token itself — treat as secret |

**Switching projects:** change `context.active-project` to another `project-id` listed under `projects`. Multiple projects from the **same account** can live in one file; for **different accounts**, keep separate files and swap the one in `.dbt/`.

**Re-download the file when** you get access to a new project, lose access to one, your token is rotated/changes, or your account host changes (e.g. region move).

**The companion `dbt-cloud` block inside `dbt_project.yml`**

```yaml
dbt-cloud:
  project-id: your_project_id     # required
  defer-env-id: '123456'          # optional
  account_id: your_account_id     # optional; dbt v2 only; note the underscore
```
It tells the platform CLI, Studio IDE and dbt v2 which platform project this local project maps to. `defer-env-id` is used for v2 auto-deferral and CLI deferral overrides.

## 11. Cheat sheet

| Key | Type | Default | Purpose |
|---|---|---|---|
| `name` | string | — (required) | Gives the project its identity. Also the key you use under `models:`, `seeds:` etc. to target your own project's resources. Letters, digits, underscores only. |
| `version` | string | `None` | Records your project's own version (semantic version like `1.0.0`). Optional from dbt 1.5; mostly informational. |
| `config-version` | int | `2` | Tells dbt which YAML structure the file uses. Only v2 is supported now, so it's optional. |
| `profile` | string | — | Links the project to a connection profile in `profiles.yml`, i.e. which warehouse and credentials to use. Overridable with `--profile`. |
| `model-paths` | list | `["models"]` | Tells dbt where to find models, sources and unit tests. Change it if your team uses a different folder name. |
| `seed-paths` | list | `["seeds"]` | Tells dbt where your seed CSV files live so `dbt seed` can load them. |
| `test-paths` | list | `["tests"]` | Where singular tests and custom generic tests (`tests/generic`) are found. |
| `analysis-paths` | list | none (init sets `analyses`) | Folder of analyses: SQL that dbt compiles (with `ref()` etc.) but never materializes. Useful for ad-hoc queries under version control. |
| `macro-paths` | list | `["macros"]` | Where reusable Jinja macros live. Can't be the same folder as models. |
| `snapshot-paths` | list | `["snapshots"]` | Where snapshot definitions (history tracking of changing data) live. |
| `docs-paths` | list | all resource paths | Limits where dbt searches for `{% docs %}` blocks used in documentation. Usually left unset. |
| `asset-paths` | list | `[]` | Files (e.g. images) copied into `target/` during `dbt docs generate` so they render in your project docs. |
| `function-paths` | list | `["functions"]` | Where user-defined functions (UDFs) are stored. |
| `osi-paths` | list | `["OSI"]` | Where Ossie semantic-layer documents are stored (dbt v1.12+). |
| `check-paths` | list | `["checks"]` | Where project checks are stored (dbt v2). |
| `skill-paths` | list | `["skills"]` | Where agent skills (folders with a `SKILL.md`) are found, in your project and installed packages. |
| `packages-install-path` | string | `dbt_packages` | Chooses the folder `dbt deps` installs packages into. Usually git-ignored. |
| `clean-targets` | list | `target-path` contents | Lists the generated folders `dbt clean` deletes (e.g. `target`, `dbt_packages`, `logs`). Only list artifacts, never source code. |
| `query-comment` | string / dict | JSON metadata comment | Adds a comment to every query dbt runs, so you can trace warehouse queries back to dbt models, users or runs (cost attribution, debugging). |
| `quoting` | dict | adapter-dependent | Controls whether dbt wraps database/schema/identifier names in quotes. Matters for case sensitivity (esp. Snowflake, Redshift) and reserved words. |
| `require-dbt-version` | string / list | none (no check) | Restricts which dbt versions can run the project, keeping teams and packages compatible. Also signals dbt v2 support. |
| `dispatch` | list of dicts | root project first | Sets the search order for macro implementations by package, letting you override or shim package macros (e.g. `dbt_utils`). |
| `on-run-start` / `on-run-end` | string / list | none | Project-wide hooks: SQL or macros run at the start or end of commands like `dbt run` or `dbt build` (e.g. grants, audit logging). |
| `dbt-cloud` | dict | — | Maps the local project to a dbt platform project (`project-id`, optional `defer-env-id`, `account_id`, `account-host`) for the platform CLI, IDE and deferral. |
